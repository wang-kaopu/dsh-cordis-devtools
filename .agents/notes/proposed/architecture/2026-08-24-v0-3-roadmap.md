# Agent Note: Define the v0.2 observer close and v0.3 waterfall instrumentation boundary

Status: proposed

## Problem

The repository has shipped the observer core plus Events, Timeline, and Fibers Web views, but the README milestone list is too small to guide the next stage safely. Two risks are increasing at the same time:

1. remaining v0.2 work spans Host diagnostics, client UX, and real-browser integration, so parallel branches can collide on shared contracts and the current monolithic client view;
2. v0.3 requires facts that `internal/dispatch` cannot provide, so moving from observer diagnostics to per-listener timing / `next()` attribution without an explicit boundary could silently change Cordis dispatch behavior or present inferred data as fact.

Cordis already provides a safe diagnostic source for v0.2 Effects work: `fiber.getEffects()` returns labeled live `EffectMeta` trees. By contrast, Cordis waterfall composes the filtered listener callbacks around a mutable `next` continuation, and skipping `next()` vetoes the rest of the chain. Those v0.3 facts require observing the actual callback/continuation execution path rather than registration state or pre-execution `internal/dispatch` metadata.

## Proposal

Treat v0.2 and v0.3 as two explicit architectural stages.

### v0.2 remains observer-only

Close v0.2 with:

- a behavior-preserving split of the current Web views into stable files so parallel UI work does not fight over one component;
- cross-navigation between Events, Timeline, and Fibers;
- Fiber Effects inspection based only on Cordis `fiber.getEffects()` label/children diagnostics;
- a minimal real DSH Web E2E/profile smoke harness;
- release hardening that preserves the existing observer invariants.

No v0.2 task may wrap target listener callbacks, replace waterfall `next()`, capture raw payloads, or claim generic listener execution/completion facts.

### v0.3 is a separate opt-in waterfall instrumented mode

The default/disabled path remains observer-only and behavior-neutral. v0.3 initially instruments only waterfall dispatch because its motivating facts are continuation-specific:

- listener entry/settlement timing;
- whether/how often `next()` is called;
- where downstream execution stops;
- a defensible relationship between listener-local and downstream elapsed work.

Before production wrapping begins, a dedicated instrumentation architecture checkpoint must decide and test the exact seam, lifecycle, identity preservation, async/error semantics, recursion/reentrancy, repeated `next()` behavior, context filtering, overhead, privacy, and Cordis-version compatibility.

A shared trace contract is frozen before storage/UI branches consume it. `selfTime` is not accepted as a field merely because it is convenient: repeated/reentrant `next()` and async work must have a precise definition first, otherwise the UI should expose narrower timing facts.

### Parallel development follows the dependency graph

The first safe parallel wave after this planning change is:

- client view split;
- Fiber Effects Host/shared snapshot work;
- real DSH Web E2E harness.

Cross-navigation starts after the view split. Effects UI follows the Host snapshot and should avoid racing a large cross-navigation edit to the same Fibers view. v0.3 production instrumentation remains blocked by its architecture checkpoint even if research/test cataloging proceeds in parallel.

The detailed work packages and dependency graph live in `docs/roadmap.md` and `docs/parallel-work.md`.

## Alternatives considered

### Start v0.3 instrumentation immediately and document it afterward

Rejected because instrumentation changes the observation boundary and can perturb the semantics/timing being measured. The callback/continuation seam, cleanup identity, and timing definitions need review before code becomes the de facto architecture.

### Keep v0.2 exactly as shipped and move directly to profiler work

Rejected because the existing Events/Timeline/Fibers views are still weakly connected, Fiber exposes a safe diagnostic `getEffects()` source that materially improves debugging, and the project still relies on manual full-DSH smoke testing. Closing those gaps creates a much stronger parity baseline for v0.3.

### Instrument every Cordis dispatch mode in v0.3

Rejected as unnecessary scope. Waterfall has unique `next()`/veto semantics and is the feature that motivated instrumentation. Parallel/serial/bail/emit profiling can be considered later with mode-specific semantics rather than forced into one generic trace model.

### Run every remaining task in parallel

Rejected because parallel edits to `src/shared/types.ts`, `src/host/cordis-adapter.ts`, or the current monolithic Web component create merge conflict and, more importantly, competing semantic contracts. Parallelism should follow disjoint ownership and frozen dependencies.

### Derive v0.3 timing from `internal/dispatch` plus current listener order

Rejected because `internal/dispatch` is pre-execution and does not prove which filtered listeners actually entered, whether `next()` ran, where the waterfall stopped, or when listener promises settled.

## Acceptance criteria

This planning proposal is ready for implementation work when:

- the repository has a roadmap with explicit v0.2 and v0.3 exit criteria;
- v0.2 observer work and v0.3 instrumented work are visibly separated;
- Fiber Effects is grounded in `fiber.getEffects()` rather than reconstructed from unrelated registries;
- v0.3 production wrapping is explicitly blocked on an architecture checkpoint;
- trace fields that are not yet semantically defined, especially `selfTime`, are not prematurely frozen;
- the parallel work document identifies dependencies, high-conflict surfaces, and at least one safe multi-branch execution wave;
- README milestone text points maintainers to the detailed roadmap instead of acting as the only plan.

## Risks

- Cordis internals may change before v0.3 implementation; instrumentation design must refresh against the actual pinned runtime rather than relying on this planning snapshot.
- `getEffects()` exposes only labeled live effect metadata, so Effects UI may be intentionally sparse for unlabeled effects; the project must not compensate by inventing labels.
- Splitting the client view can become an unnecessary architecture exercise if it changes behavior; keep O1 mechanical and evidence-driven.
- A trace contract can still overfit simple single-`next()` examples. Repeated `next()`, nested waterfall, async errors, and filtering need first-class fixtures before fields are called stable.
- Parallel work can become slower than serial work when branches share contracts. The dependency graph is guidance to reduce contention, not a requirement to maximize branch count.
