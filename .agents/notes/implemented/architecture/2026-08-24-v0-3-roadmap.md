# Agent Note: Define the v0.2 observer close and v0.3 waterfall instrumentation boundary

Status: implemented

## Problem

The observer core plus Events/Timeline/Fibers Web views needed a safe path to v0.2 closure and then to execution-time waterfall profiling. The key boundary was that `internal/dispatch` is pre-execution: it cannot prove which listeners entered, whether/how `next()` ran, or when async listeners settled.

Without an explicit milestone/parallelization plan, remaining observer work could collide on shared client/contracts while v0.3 could accidentally turn inferred facts into authoritative profiler data.

## Decision

Treat v0.2 and v0.3 as separate architectural stages.

### v0.2 remains observer-only

Close v0.2 with:

- behavior-preserving Web view split;
- Events/Timeline/Fibers cross-navigation;
- Fiber Effects inspection based only on `fiber.getEffects()` label/children metadata;
- real DSH Web E2E;
- observer release hardening.

No v0.2 task wraps target callbacks, replaces waterfall `next()`, captures raw payloads, or claims listener execution/completion facts unavailable from observer signals.

### v0.3 is explicit opt-in waterfall instrumentation

The default path remains the v0.2 observer path. v0.3 instruments waterfall only and requires an approved architecture checkpoint before production instrumentation.

The profiler contract is frozen before storage/UI consumers. Fields require precise semantics; in particular `selfTime` and irreversible chain-stop conclusions are not accepted merely because they are convenient for UI.

### Parallel work follows dependencies

Independent observer/client/Host/E2E work may run concurrently when file ownership is disjoint. Shared contracts and high-conflict shell/adapter surfaces remain serialized. The execution plan was recorded in `docs/parallel-work.md`.

## Alternatives considered

### Start v0.3 instrumentation immediately and document afterward

Rejected. Instrumentation changes the observation boundary, so seam/lifecycle/identity/async/error/privacy semantics needed review before code established accidental architecture.

### Stop v0.2 where it was and move directly to profiler work

Rejected. Cross-navigation, Effects, stable client view ownership, and real-browser evidence materially strengthened the observer baseline used later by parity testing.

### Instrument every dispatch mode in v0.3

Rejected. Waterfall has continuation-specific semantics and was the motivating requirement. `emit` / `parallel` / `serial` / `bail` need their own future semantics rather than being forced into one generic model.

### Run all remaining work in parallel

Rejected. Parallel edits to shared contracts, the same client shell/view, or the Cordis compatibility boundary create semantic races as well as merge conflicts.

### Derive timing from `internal/dispatch` + listener order

Rejected. A pre-execution dispatch signal cannot prove listener entry, filtering result, continuation behavior, or settlement timing.

## Consequences

The plan was executed through O1–O5 and I0–I6:

- v0.2 closed as an observer-only Web DevTools baseline;
- v0.3 received a dedicated architecture checkpoint, trace contract, real behavior matrix, explicit instrumentation core, semantic parity/overhead evidence, bounded trace transport, Profiler UI, and release hardening;
- observer and profiler transports/stores remain separate;
- production v0.3 still does not expose `selfTime`, definitive `shortCircuit`/`veto`, raw payload capture, or generic non-waterfall profiling;
- `docs/parallel-work.md` is now retained as a historical execution record rather than an active backlog.
