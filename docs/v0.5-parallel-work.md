# v0.5 Parallel Development Plan — Runtime Verification

This plan maximizes useful concurrency without duplicating the verification contract or creating avoidable conflicts in shared files.

## Dependency graph

```text
A — docs / architecture decision
        │
        ▼
B — shared verification contract
        │
        ├──────────────┬──────────────┐
        ▼              ▼              ▼
C — checkpoint     D — diff       E — real Cordis
    projection         engine          fixture
        │              │              │
        └──────┬───────┘              │
               ▼                      │
        F — query integration         │
               │                      │
          ┌────┴────┐                 │
          ▼         ▼                 │
     G1 — DSH   G2 — MCP              │
          └────┬────┘                 │
               └──────────┬───────────┘
                          ▼
                 H — combined real DSH E2E
                          │
                          ▼
                 I — repository closeout
```

The largest safe fan-out is immediately after Wave B: **C, D, and E can proceed independently**.

A second fan-out happens after F: **G1 and G2 can proceed independently**.

## Why Wave B is intentionally sequential

Checkpoint projection, semantic diff, DSH schemas, and MCP schemas all depend on the same serialized contract. Letting several branches invent that contract independently creates expensive reconciliation and semantic drift.

Wave B should therefore be a small PR that lands first. It fixes names and transport-neutral types but contains little or no runtime logic.

After it lands, downstream branches can stay narrow.

## Branching strategy

Prefer short-lived stacked branches only where there is a real dependency.

### First fan-out

```text
main + V1
  ├─ V2 checkpoint
  ├─ V3 diff
  └─ V4 fixture
```

V2/V3 should merge independently once green. Do not merge one implementation branch into the other merely to make progress.

### Integration gate

V5 starts from main after V2/V3. If one finishes much earlier, V5 still waits for both because its job is to wire the final shared behavior once.

### Second fan-out

```text
main + V5
  ├─ V6 Cordis Inspect
  └─ V7 MCP
```

V6/V7 must not copy checkpoint/diff logic into adapters.

### Final integration

V8 starts from main after V4/V6/V7. It owns all combined real-DSH orchestration and is merged only after both adapters prove the same semantic transition.

## Auto-merge policy for this milestone

When maintainer authorization for automatic merge remains active:

- merge a PR only after its required CI is green;
- parents/shared-contract PRs land before dependent PRs are retargeted;
- use integration merges/rebases only to preserve both sibling implementations when they touch a shared entry file;
- never resolve semantic conflicts by dropping one sibling's behavior;
- final E2E and closeout PRs are squash-merge candidates after the dependency stack has landed.

If implementation reveals a new decision-sensitive issue that changes the approved contract, stop that branch, update the proposal/roadmap, and surface the decision rather than auto-merging a scope change.

## What not to parallelize

Do not parallelize these decisions into competing implementations:

- checkpoint schema shape;
- semantic identity rules;
- whether runtime-local uid/id participates in cross-checkpoint matching;
- digest canonicalization rules;
- checkpoint scope closure semantics;
- root-cause/fix verdict semantics;
- profiler mutation policy.

Those are shared product/contract decisions and belong in the architecture/contract gates.

## Expected maximum concurrency

Peak useful concurrency is three branches during Waves C/D/E, then two branches during G1/G2.

```text
Peak 1: checkpoint | diff | fixture
Peak 2: DSH adapter | MCP adapter
```

Trying to run more branches in parallel would mostly create contention on `src/host/diagnostics.ts`, shared types, or the single real DSH E2E orchestrator without increasing actual throughput.
