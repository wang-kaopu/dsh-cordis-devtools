# v0.4 — Agent Runtime Diagnostics

## Product statement

`dsh-cordis-devtools` evolves from a human-only runtime panel into a shared Cordis runtime diagnostics layer for both developers and coding agents.

The human DevTools UI remains a first-class evidence viewer, but it is no longer the only client. v0.4 adds two agent-facing adapters over the same runtime facts:

1. **DSH-native Cordis Inspect Provider** for in-process DSH agents;
2. **embedded MCP server** for external agents such as Codex, Claude Code, and Cursor.

The product promise is:

> A coding agent can inspect the same live Cordis runtime that a developer sees in Cordis DevTools, without requiring the developer to open the panel or copy screenshots/logs.

## Why this is not source-code inference

Source code and the existing DSH capability inspectors can answer what a plugin *declares* or what APIs *exist*. They cannot reliably establish runtime facts such as:

- whether a listener is currently registered;
- whether one source-level registration exists as multiple live registrations after reload/HMR;
- which live Fiber currently owns a listener;
- whether an old Fiber still exists;
- whether an event occurred inside the retained dispatch window;
- what bounded waterfall trace facts were actually observed.

v0.4 therefore exposes runtime ground truth rather than another code-analysis layer.

## Architecture

```text
                         Cordis Runtime
                              │
              ┌───────────────┴────────────────┐
              │                                │
       ObserverCollector            WaterfallTraceStore
              │                                │
              └───────────────┬────────────────┘
                              ▼
                       DevtoolsService
                              │
                              ▼
                  Runtime Diagnostics Query
                       transport-neutral
                     /          |          \
                    /           |           \
                   ▼            ▼            ▼
          Human DevTools   Cordis Inspect   MCP Adapter
              UI             Provider       loopback HTTP
                               │               │
                               ▼               ▼
                           DSH Agent      External Agents
```

The **Runtime Diagnostics Query** layer owns filtering and evidence semantics. Neither Cordis Inspect nor MCP reimplements snapshot traversal.

## Core principles

### 1. Facts, not diagnoses

The diagnostics layer returns runtime evidence. The model is responsible for reasoning from that evidence.

The project does not add a `diagnose()` API that manufactures `likelyCause`, `confidence`, or hidden heuristics. `unknown` remains preferable to a fabricated conclusion.

### 2. One contract, multiple adapters

DSH Cordis Inspect and MCP expose the same logical methods and result semantics. Adapter-specific naming is allowed, but fields and evidence meaning must not drift.

### 3. Read-only first

The first v0.4 agent surface is read-only:

- runtime summary;
- event inspection;
- Fiber inspection;
- recent dispatch search;
- reading already-existing profiler traces.

Profiler enable/disable remains explicitly deferred because instrumentation changes runtime behavior and requires a separate permission/mutation design.

### 4. Bounded evidence stays bounded

An empty dispatch result means only “not observed in the retained window,” never “this event never happened.” Query results must carry enough metadata for an agent to preserve that distinction.

### 5. Metadata-first privacy remains unchanged

Agent adapters do not introduce raw event arguments, return values, error messages, prompts, tool results, file contents, config, credentials, or raw effect functions.

## Runtime query contract

v0.4 starts with five logical queries.

### `runtimeSummary()`

Purpose: cheap runtime discovery before a narrower query.

Returns counts and evidence-window metadata such as:

- generated timestamp;
- live Fiber count;
- event/listener counts;
- retained dispatch count and bounded flag;
- profiler instrumentation state and retained trace count.

It does not return the full snapshot.

### `inspectEvent({ name })`

Purpose: answer what is *actually registered now* for one event.

Returns:

- exact event name;
- current listener count;
- ordered listener metadata;
- listener owner references;
- whether each referenced owner uid is currently present in authoritative live Fiber inventory.

An unknown event is represented as a successful “not found” domain result rather than fabricated empty registration data.

### `inspectFiber({ uid | name })`

Purpose: inspect authoritative live Fiber state.

Rules:

- `uid` is exact when supplied;
- `name` may match multiple Fibers and therefore returns a result set;
- only authoritative live inventory is returned as live Fiber state;
- historical owner references are not promoted into this result.

The query may include parent, inject names, effects, owned listeners/events, and retained dispatch-context hit counts derived from the same bounded observer snapshot.

### `searchDispatches({ event?, fiberUid?, mode?, limit? })`

Purpose: search the retained observer dispatch window without sending the entire snapshot to the model.

Returns:

- matching records in newest-first order;
- number returned;
- configured/known bounded-window semantics;
- whether the caller-supplied limit truncated matching records.

The result never claims execution completion or listener timing because observer dispatch records do not contain those facts.

### `profilerTraces({ event?, limit? })`

Purpose: read already-recorded waterfall profiler evidence.

Returns:

- current instrumentation state;
- matching retained traces;
- bounded/truncation metadata.

Calling this query never enables instrumentation.

## DSH-native integration

When the DSH Host exposes `cordisInspect`, the plugin registers one Host provider backed by Runtime Diagnostics Query.

Suggested provider identity:

```text
provider: CordisRuntime
platform: host
```

Methods mirror the logical query names:

```text
runtimeSummary
inspectEvent
inspectFiber
searchDispatches
profilerTraces
```

DSH agents discover the provider through the existing `cordis_inspect_list` tool and invoke it through `cordis_inspect_query`. The plugin does not register a second parallel set of DSH model tools.

The Provider is lifecycle-owned by the plugin Fiber and disappears when the plugin is disposed.

## External MCP integration

The running DSH Host may expose an embedded MCP endpoint that queries the same Runtime Diagnostics Query instance.

### Transport

First implementation target:

```text
Streamable HTTP
127.0.0.1 only
```

The MCP server belongs to the currently running DSH process. An external MCP process that creates a separate Cordis runtime would inspect the wrong system and is therefore rejected as the primary architecture.

### Tool names

Initial MCP surface:

```text
cordis_runtime_summary
cordis_inspect_event
cordis_inspect_fiber
cordis_search_dispatches
cordis_profiler_traces
```

### Security boundary

v0.4 read-only MCP must:

- bind only to loopback;
- reject configuration that requests a non-loopback host;
- avoid raw sensitive payloads by contract;
- tie server shutdown to plugin disposal;
- surface bind/startup failure instead of silently falling back to a wider interface.

Authentication/token support may be added within v0.4 if needed by the chosen transport implementation, but remote/LAN exposure is explicitly out of scope.

### Discovery/configuration

The first implementation may use an explicit configured port. Automatic discovery files, generated client snippets, stdio forwarding, and multi-runtime selection are follow-up UX work once the protocol path is proven.

## Human UI relationship

Events, Timeline, Fibers, and Profiler continue to exist. They are the human-readable view of the same runtime, not a prerequisite for Agent access.

The UI is allowed to remain richer in presentation while the Agent APIs remain compact and machine-oriented.

## Verification strategy

v0.4 requires evidence at four layers:

1. **pure query tests** — deterministic filtering, ordering, live/historical semantics, bounded/truncated metadata;
2. **real Cordis integration** — live listener/Fiber ownership and observer dispatch facts remain authoritative;
3. **DSH Cordis Inspect adapter tests** — provider registration, manifest/schema, query delegation, disposal;
4. **MCP protocol integration** — a real MCP client connects to the embedded loopback server, lists tools, and obtains the same canonical facts as direct query calls.

A later end-to-end benchmark should deliberately create a runtime-only failure such as duplicate live listener ownership and compare whether an agent can identify it through diagnostics without panel interaction.

## Explicit non-goals for the first v0.4 slice

- no generic AI root-cause diagnosis API;
- no source-code analysis duplication;
- no profiler auto-enable;
- no mutating runtime tools;
- no raw payload capture;
- no remote/LAN MCP exposure;
- no persistent/lossless telemetry store;
- no promise of complete dispatch history;
- no stdio bridge until embedded Streamable HTTP is proven;
- no redesign of the existing DevTools UI.

## Success criteria

v0.4 is successful when all of the following are true:

1. a DSH Agent can discover `CordisRuntime` and query live event/Fiber/dispatch facts without opening the DevTools panel;
2. an external MCP client connected to the same running DSH process can query the same facts;
3. both paths share one transport-neutral query implementation and consistent evidence semantics;
4. default observer behavior remains behavior-neutral;
5. an empty/partial result cannot be mistaken for lossless historical proof;
6. disabling/removing the plugin removes both Agent-facing registrations and server resources.
