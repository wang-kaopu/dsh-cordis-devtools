# v0.5 Product Design — Runtime Verification

## Summary

v0.4 lets humans, the in-process DSH Agent, and external MCP clients inspect the same live Cordis runtime. v0.5 extends that read-only diagnostic surface with **before/after runtime verification**.

The milestone goal is:

> A coding Agent can capture the relevant runtime topology before a change, edit/reload code, compare the current runtime with the baseline, and report the concrete runtime facts that changed.

v0.5 remains **read-only with respect to the target Cordis runtime**. It does not automatically enable the waterfall profiler, mutate listener registrations, reload plugins, or make root-cause/fix claims on behalf of the Agent.

## User experience

The intended Agent loop is:

```text
inspect current problem
        ↓
captureCheckpoint
        ↓
edit source / reload by normal development workflow
        ↓
compareCurrent(baseline)
        ↓
inspect changed facts when needed
        ↓
Agent explains whether the expected runtime condition is now present
```

Example:

```text
Before
  SessionPlugin live Fiber multiplicity = 2
  session/created listener multiplicity owned by SessionPlugin = 2

After
  SessionPlugin live Fiber multiplicity = 1
  session/created listener multiplicity owned by SessionPlugin = 1
```

The diagnostics layer reports only those facts. It does not return `fixed: true`, `rootCause`, or a confidence score.

## Why a first-class checkpoint/diff layer is needed

An Agent could ask the v0.4 queries twice and manually compare the results, but that has three problems:

1. runtime-local ids are noisy across reloads;
2. bounded dispatch history must not be confused with authoritative live state;
3. every Agent would need to reimplement the same matching, multiplicity, and unknown semantics.

v0.5 therefore adds a canonical verification projection and diff algorithm rather than asking models to compare arbitrary snapshots.

## Core architecture

```text
Cordis runtime
     │
     ▼
DevtoolsService / observer facts
     │
     ▼
Runtime Diagnostics Query
     │
     ├─────────────── v0.4 targeted reads
     │
     ▼
Runtime Verification
  ├─ checkpoint projection
  ├─ semantic canonicalization
  └─ checkpoint diff
     │
     ├─────────────────────┐
     ▼                     ▼
CordisRuntime Inspect      embedded MCP
DSH Agent                  external Agent
```

The verification layer consumes existing project-owned runtime snapshots. It must not add new direct Cordis-internal access outside `src/host/cordis-adapter.ts`.

## Checkpoint contract

### Self-contained, not server-persistent

A checkpoint is a **serializable value returned to the caller**, not an opaque id stored in a Host-side database.

Conceptually:

```ts
interface RuntimeCheckpoint {
  schemaVersion: 1
  capturedAt: number
  scope: RuntimeCheckpointScope
  digest: string
  events: RuntimeCheckpointEvent[]
  listeners: RuntimeCheckpointListener[]
  fibers: RuntimeCheckpointFiber[]
}
```

The exact TypeScript shape is finalized in the shared-contract implementation PR, but these semantics are mandatory.

This design is preferred because it:

- works across plugin reload or Host restart as long as the Agent still has the artifact;
- avoids checkpoint TTL, ownership, persistence, and multi-Agent cleanup state;
- keeps DSH Cordis Inspect conceptually read-only;
- lets DSH and MCP expose the same canonical value;
- makes checkpoint comparison deterministic and testable as a pure function.

### Schema version and digest

Every checkpoint carries a schema version. Comparison rejects unsupported versions rather than guessing compatibility.

A digest is computed over the canonical semantic payload. It is used for integrity/equality checks, not as a substitute for evidence.

### Scope

The first implementation supports an optional exact-name scope:

```ts
interface RuntimeCheckpointScope {
  eventNames?: string[]
  fiberNames?: string[]
}
```

Rules:

- omitted selectors capture the current authoritative topology;
- event selectors include matching events/listeners and the current owner Fibers required to preserve their relationships;
- Fiber-name selectors include matching live Fibers and their owned current listener/event relationships;
- both selectors use union semantics;
- selectors are exact names, not regex/fuzzy matching;
- the scope is stored in the checkpoint and reused automatically by `compareCurrent`.

The implementation should keep the scope rules deterministic and one-hop. It must not recursively crawl arbitrary service/object graphs.

## What belongs in a checkpoint

A checkpoint contains **current authoritative topology**, including enough metadata to verify:

- event existence and live listener multiplicity;
- listener event/order/flags and owning Fiber semantic metadata;
- live Fiber multiplicity, state, parent name, inject names, owned event relationships;
- metadata-only Effect label structure or an equivalent canonical metadata projection.

Runtime-local ids/uids may be retained as capture-local evidence for navigation, but they are **not cross-checkpoint identity keys**.

## What is deliberately excluded

### Bounded dispatch history

Dispatch records are not part of the default checkpoint state. They are a bounded occurrence window, not authoritative current topology.

An Agent that needs to verify that an event occurred after a change should continue to call `searchDispatches` and preserve its `bounded/truncated` semantics.

### Profiler traces

Profiler traces are also excluded from checkpoint topology. Existing `profilerTraces` remains the read path for retained traces.

### Raw/sensitive payloads

Checkpointing does not add raw event arguments, return values, errors, prompts, tool results, file contents, plugin config, credentials, or raw Effect functions/disposers.

## Cross-checkpoint identity rules

The diff must never assume that runtime-local ids survive reload.

For example, this is not a safe cross-checkpoint conclusion:

```text
uid 41 disappeared, therefore that exact plugin instance was fixed
```

The default comparison is semantic and multiplicity-based.

### Listener semantic descriptor

A listener comparison descriptor is based on stable observable metadata such as:

```text
event name
owner Fiber name / no owner
execution order
prepend
global
```

The runtime-local listener id and owner uid are excluded from its semantic key.

### Fiber semantic descriptor

A Fiber comparison descriptor is based on metadata such as:

```text
Fiber name
normalized state
parent Fiber name / no parent
sorted inject names
sorted owned event names
canonical metadata-only Effect labels/paths
```

The Fiber uid is excluded from its semantic key.

Duplicate equal descriptors are preserved as a **multiset count**. This is essential for the v0.4 duplicate-Fiber problem: two semantically equivalent live instances must compare as count `2`, not collapse into one row.

## Diff contract

The machine-facing operation is conceptually:

```ts
captureCheckpoint(scope?) -> RuntimeCheckpoint
compareCurrent({ baseline }) -> RuntimeCheckpointComparison
```

`compareCurrent`:

1. validates the baseline schema/digest;
2. captures the current runtime using the baseline scope;
3. compares semantic multisets;
4. returns the current checkpoint plus structured changes.

Conceptual result:

```json
{
  "changed": true,
  "baselineDigest": "...",
  "current": { "schemaVersion": 1, "digest": "..." },
  "events": [
    {
      "name": "session/created",
      "beforeListenerCount": 2,
      "afterListenerCount": 1
    }
  ],
  "listenerGroups": [
    {
      "descriptor": {
        "event": "session/created",
        "ownerName": "SessionPlugin",
        "order": 0,
        "prepend": false,
        "global": false
      },
      "beforeCount": 2,
      "afterCount": 1,
      "delta": -1
    }
  ],
  "fiberGroups": [
    {
      "descriptor": {
        "name": "SessionPlugin"
      },
      "beforeCount": 2,
      "afterCount": 1,
      "delta": -1
    }
  ]
}
```

The implementation may expose richer structural details, but it must preserve these principles:

- multiplicity is explicit;
- unchanged runtime-local ids do not create false semantic changes;
- changed runtime-local ids alone do not create false semantic changes;
- no `fixed`, `rootCause`, or confidence field is produced;
- empty/unchanged results mean only that the captured authoritative topology is semantically equal for the checkpoint scope.

## Agent-facing methods

### DSH Cordis Inspect

The existing `CordisRuntime` Provider should add the logical methods:

```text
captureCheckpoint
compareCurrent
```

They remain read-only with respect to the target Cordis runtime.

No second package-specific DSH tool family is introduced.

### MCP

The embedded MCP adapter should add:

```text
cordis_capture_checkpoint
cordis_compare_current
```

They delegate to the same verification implementation used by Cordis Inspect.

MCP continues to be loopback-only and disabled by default at server level. These tools do not enable instrumentation and should be annotated read-only/idempotent when the final implementation satisfies those protocol semantics.

## Verification scenario

The canonical v0.5 proof extends the duplicate-Fiber fixture:

```text
baseline runtime
  two same-name live Fibers
  two listeners for one event
        ↓
captureCheckpoint
        ↓
real Cordis lifecycle transition
  one duplicate instance is disposed/replaced
        ↓
compareCurrent
        ↓
semantic diff
  Fiber group 2 → 1
  listener group 2 → 1
```

The proof deliberately changes runtime-local ids so the suite demonstrates that semantic verification is not accidentally uid-based.

The final real DSH smoke should prove both paths against the same runtime transition:

```text
DSH Cordis Inspect → checkpoint / compare
external MCP       → checkpoint / compare
Human UI           → existing runtime remains healthy
```

No model credential or API key is required for the test.

## Non-goals for v0.5

The following are explicitly deferred:

- automatic plugin/source reload control;
- `diagnose()` or model-independent root-cause heuristics;
- server-persistent checkpoint ids/history;
- persistent checkpoint files;
- multi-runtime checkpoint discovery;
- profiler enable/disable tools;
- profiling lease/timeout/permission logic;
- remote/LAN MCP;
- payload capture;
- generic lossless telemetry.

## Why profiler mutation moves to v0.6

Profiler mutation has a different trust boundary from checkpoint/diff:

- it changes the runtime dispatch seam;
- it needs permission policy;
- it needs ownership/timeout cleanup if an Agent disappears;
- it must handle conflict/unsupported instrumentation states.

Keeping v0.5 read-only gives the project a clean progression:

```text
v0.4  Agent can observe runtime facts
v0.5  Agent can verify before/after runtime facts
v0.6  Agent may perform controlled runtime experiments
```

## v0.5 completion definition

v0.5 is repository-ready when:

- the checkpoint schema/canonicalization is versioned and tested;
- semantic diff preserves duplicate multiplicity and ignores runtime-local id churn;
- `captureCheckpoint` and `compareCurrent` are available through the shared query path;
- DSH Cordis Inspect exposes them without a duplicate tool family;
- MCP exposes equivalent tools with canonical result parity;
- one real DSH test proves duplicate runtime state `2 → 1` through both Agent paths;
- existing observer/UI/profiler behavior remains green;
- README/roadmap/package repository version are closed out to `0.5.0` only after implementation lands.

Publishing npm, creating a Git tag, or creating a GitHub Release remains a separate explicit action.
