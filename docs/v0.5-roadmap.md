# v0.5 Roadmap — Runtime Verification

v0.5 starts from repository version `0.4.0`, where Human DevTools, DSH Cordis Inspect, and embedded MCP already share one read-only Runtime Diagnostics Query layer.

## Milestone goal

A coding Agent can:

1. inspect a runtime problem;
2. capture a canonical read-only checkpoint;
3. edit/reload code through the normal development workflow;
4. compare the current runtime with the baseline;
5. explain the concrete runtime facts that changed.

The diagnostics package reports facts and diffs. It does not claim that a bug is fixed or infer root cause.

## Product boundary

v0.5 remains read-only with respect to the target Cordis runtime.

Included:

- versioned self-contained runtime checkpoints;
- exact-name checkpoint scoping;
- canonical semantic projection;
- multiplicity-preserving semantic diff;
- `captureCheckpoint` / `compareCurrent` query methods;
- DSH Cordis Inspect exposure;
- MCP exposure;
- real DSH before/after verification proof.

Deferred:

- automatic source/plugin reload control;
- profiler enable/disable Agent tools;
- profiling lease/timeout/permission;
- server-persistent checkpoint storage;
- `diagnose()`/confidence heuristics;
- remote MCP;
- payload capture.

## Wave A — Contract and architecture

Status: planned by the v0.5 documentation PR.

Deliverables:

- [ ] product design approved;
- [ ] checkpoint state-vs-history boundary fixed;
- [ ] cross-reload identity semantics fixed;
- [ ] checkpoint schema versioning/digest semantics fixed;
- [ ] diff semantics fixed;
- [ ] DSH/MCP adapter boundary fixed;
- [ ] parallel dependency graph fixed.

Acceptance:

- no runtime-local id is treated as a cross-checkpoint identity key;
- duplicate semantic instances remain count-preserving;
- bounded dispatch/profiler histories are not silently promoted into authoritative checkpoint state;
- mutation remains outside v0.5.

## Wave B — Shared verification contract

This is the small sequential gate before implementation fans out.

Deliverables:

- [ ] `src/shared/verification.ts` (or equivalent) owns serializable v1 checkpoint/diff types;
- [ ] schema version is explicit;
- [ ] scope contract supports exact event/Fiber names;
- [ ] comparison output separates event/listener/Fiber changes;
- [ ] public exports are updated;
- [ ] Agent Note records the final implemented contract.

Acceptance:

- types do not depend on MCP or DSH-specific transport types;
- shared types contain no raw Cordis internals/functions;
- the contract can represent duplicate descriptors through counts.

## Wave C — Checkpoint projection

Can run in parallel with Waves D and E after Wave B lands.

Deliverables:

- [ ] pure checkpoint projection from project-owned `DevtoolsSnapshot` facts;
- [ ] exact-name scope normalization;
- [ ] deterministic one-hop relationship closure;
- [ ] canonical ordering;
- [ ] metadata-only Effect canonicalization;
- [ ] digest generation/validation;
- [ ] tests for full and scoped checkpoints.

Acceptance:

- reordering input arrays does not change the canonical semantic result/digest;
- runtime-local listener/Fiber ids do not influence the semantic digest;
- two duplicate equivalent Fibers/listeners remain multiplicity `2`;
- no dispatch/profiler history is included as authoritative topology.

## Wave D — Semantic diff engine

Can run in parallel with Waves C and E after Wave B lands.

Deliverables:

- [ ] pure checkpoint validation;
- [ ] semantic multiset grouping;
- [ ] event listener-count diff;
- [ ] listener descriptor count diff;
- [ ] Fiber descriptor count diff;
- [ ] unchanged/digest fast path where safe;
- [ ] tests for id churn, duplicate `2 → 1`, add/remove, structural change, invalid schema/digest.

Acceptance:

- changing only uids/listener ids produces no semantic diff;
- duplicate count `2 → 1` produces one count delta rather than arbitrary instance pairing;
- unsupported/tampered checkpoint input fails explicitly;
- diff emits no root-cause/fix/confidence claim.

## Wave E — Real Cordis verification fixture

Can run in parallel with Waves C and D after Wave B lands.

Deliverables:

- [ ] extend/create an E2E-only verification fixture;
- [ ] initial state contains two same-name live Fibers with duplicate listener ownership;
- [ ] deterministic real Cordis lifecycle transition reduces the semantic multiplicity to one;
- [ ] transition changes runtime-local ids where practical so uid-independent comparison is exercised;
- [ ] fixture remains outside published package files.

Acceptance:

- the fixture uses real Cordis lifecycle behavior, not a fake checkpoint object;
- no model credential/API key is required;
- no production runtime behavior is introduced solely for the fixture.

## Wave F — Query integration

Starts after Waves C and D land.

Deliverables:

- [ ] Runtime Diagnostics/Verification query composes checkpoint projection + diff;
- [ ] `captureCheckpoint(scope?)`;
- [ ] `compareCurrent({ baseline })`;
- [ ] `compareCurrent` automatically recaptures with the baseline scope;
- [ ] result returns current checkpoint plus structured semantic changes;
- [ ] integration tests prove canonical output.

Acceptance:

- both operations remain read-only with respect to the target Cordis runtime;
- baseline schema/digest is validated before comparison;
- existing five v0.4 queries remain behavior-compatible.

## Wave G — Agent adapters

Wave G fans out after Wave F.

### G1 — DSH Cordis Inspect

- [ ] add `captureCheckpoint`;
- [ ] add `compareCurrent`;
- [ ] schemas match the shared verification contract;
- [ ] delegate without reimplementing checkpoint/diff logic;
- [ ] real registry/provider tests remain green.

### G2 — MCP

- [ ] add `cordis_capture_checkpoint`;
- [ ] add `cordis_compare_current`;
- [ ] delegate to the same implementation;
- [ ] canonical result parity vs direct query;
- [ ] preserve loopback/read-only security boundary.

Acceptance:

- DSH does not route through MCP;
- MCP does not implement a second diff algorithm;
- equivalent inputs produce equivalent canonical facts through both adapters.

## Wave H — Combined real DSH verification proof

Starts after G1 + G2 + Wave E.

Scenario:

```text
real DSH runtime
  duplicate Fiber/listener count = 2
        ↓
DSH Inspect captureCheckpoint
MCP captureCheckpoint
        ↓
real Cordis lifecycle transition
        ↓
DSH Inspect compareCurrent
MCP compareCurrent
        ↓
both report semantic 2 → 1
        ↓
existing Human UI/profiler smoke remains healthy
```

Deliverables:

- [ ] one deterministic same-runtime proof for both Agent paths;
- [ ] semantic parity assertions;
- [ ] runtime-local id churn does not create false changes;
- [ ] current Human DevTools regression assertions stay intact.

## Wave I — Repository closeout

Only after Waves B–H land.

Deliverables:

- [ ] architecture/product docs updated from planned → implemented;
- [ ] README documents v0.5 verification workflow;
- [ ] `package.json` repository version becomes `0.5.0`;
- [ ] release-hardening CI all green;
- [ ] completed planning docs are accurate.

Publishing npm, creating a Git tag, or creating a GitHub Release is not part of this wave unless explicitly requested.

## Completion definition

v0.5 is complete at repository level when Waves A–I are satisfied and the final real DSH test proves that both DSH Cordis Inspect and external MCP can carry the same baseline across a real lifecycle change and recover the same semantic runtime diff.

## Next version boundary

Controlled runtime experiments belong to v0.6, including profiler mutation, profiling leases, permission policy, timeout/cleanup, and conflict ownership semantics.
