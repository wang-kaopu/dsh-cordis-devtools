# v0.6 Parallel Development Plan — Controlled Runtime Experiments

This plan maximizes useful concurrency while keeping instrumentation ownership, approval, and authentication decisions centralized.

## Dependency graph

```text
A — architecture / authority contract
        │
        ▼
B — shared experiment contract
        │
        ├──────────────┬──────────────┬──────────────┐
        ▼              ▼              ▼              ▼
C — lease          D — trace      E — DSH       F — MCP auth /
    coordinator        tagging        adapter        capability
        │              │              │              │
        └──────┬───────┘              │              │
               ▼                      │              │
        G — service/control           │              │
            integration               │              │
               │                      │              │
          ┌────┴───────────────┬──────┴───────┐      │
          ▼                    ▼              ▼      ▼
     H1 — DSH live        H3 — Human UI   H2 — MCP live
          wiring               ownership       wiring
          └───────────────┬────┴───────────────┘
                          ▼
                 I — combined real DSH E2E
                          │
                          ▼
                 J — repository closeout
```

Peak useful concurrency after B is four independent branches: coordinator, trace tagging, DSH authority adapter, and MCP auth/capability helper.

A second fan-out after G allows DSH live wiring, MCP live wiring, and Human UI ownership work to proceed independently.

## Why A and B are sequential

These decisions cannot safely be invented by sibling branches:

- who owns the instrumentation seam;
- whether Human can stop an Agent lease;
- whether stop needs approval;
- DSH approval failure semantics;
- external MCP authentication/capability policy;
- lease TTL/ownership semantics;
- how traces are associated with an experiment.

If several branches implement those independently, they will create incompatible authority models rather than useful parallelism.

## First fan-out

After X1:

```text
main + X1
  ├─ X2 coordinator
  ├─ X3 trace tagging
  ├─ X4 DSH approval adapter
  └─ X5 MCP auth helper
```

Rules:

- X2 and X3 do not edit `service.ts`;
- X4 and X5 depend on an abstract control contract, not a private fake copy of coordinator semantics;
- no branch edits `index.ts` merely to prove its isolated implementation;
- each branch can merge independently when green.

## Integration gate

X6 waits for X2 + X3 because it is where low-level controller ownership and trace ownership become one production path.

Do not merge X4 or X5 into X6 just to avoid later wiring; their purpose is to stay independently reviewable authority/transport adapters.

## Second fan-out

After X6:

```text
main + X6
  ├─ X7 DSH live wiring
  ├─ X8 MCP live wiring
  └─ X9 Human UI ownership
```

Potential entry/config collisions should be resolved only when real. Prefer isolated installer/config modules over having all three branches edit `src/index.ts`.

## Final integration

X10 starts only when all three production surfaces are green.

The final E2E must not use source-string assertions or model/API credentials. Prefer real DSH ToolRuntime, real approval service/answerer plumbing, official MCP SDK Client, real Cordis waterfall probe, and Chromium for Human UI.

## Auto-merge policy

The maintainer's existing auto-merge authorization may be used for implementation PRs only after the architecture decision is approved.

After approval:

- merge each independent PR only after its required CI is green;
- merge shared parents before dependent branches are retargeted/wired;
- never resolve an ownership/security conflict by dropping one sibling's behavior;
- if implementation reveals a new decision-sensitive authority question, stop that branch and update the architecture Note before merging;
- X10 and X11 are squash-merge candidates after the stack has landed.

## What not to parallelize

Do not create competing implementations for:

- owner state vocabulary;
- lease id/TTL semantics;
- Human force-stop policy;
- whether stop requires approval;
- DSH approval outcome handling;
- MCP token/capability policy;
- experiment trace association;
- conflict/unsupported cleanup rules.

These are architecture decisions, not throughput opportunities.

## Expected maximum concurrency

```text
Peak 1: coordinator | trace tagging | DSH adapter | MCP auth
Peak 2: DSH wiring | MCP wiring | Human UI
```

More parallel branches would mostly contend on `service.ts`, `index.ts`, `mcp.ts`, or the single real-DSH orchestrator without increasing useful throughput.
